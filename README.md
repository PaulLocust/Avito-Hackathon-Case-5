# Антискам тренажёр

Интерактивный тренажёр безопасных сделок для классифайда. Пользователь
выбирает роль покупателя или продавца, проходит симуляцию диалога с
контрагентом, принимает решения в спорных моментах, видит последствия выбора
и получает объяснение, какие признаки риска присутствовали в сценарии.

Цель продукта — перенос опыта тренировки в реальные сделки: научиться
распознавать тревожные признаки **до** совершения рискованного действия.

> Решение по [Кейсу 5](Кейс%205.pdf). Требования, прецеденты и обоснования
> решений — в [`Сase-analysis.md`](Сase-analysis.md).

## Быстрый старт

Нужен только Docker с плагином Compose.

```bash
docker compose up --build
```

Поднимается PostgreSQL, применяются миграции, загружается контент из
[`backend/seed/`](backend/seed/), стартуют API и интерфейс. Дополнительных
шагов не требуется — витрина сразу заполнена пятью сценариями.

| Что | Адрес |
|---|---|
| **Интерфейс** | **http://localhost:3000** |
| API | http://localhost:8080 |
| Проба готовности | http://localhost:8080/readyz |
| Метрики Prometheus | http://localhost:8080/metrics |

Проверить, что всё поднялось:

```bash
curl -s http://localhost:8080/api/v1/scenarios
```

Остановить с сохранением данных — `docker compose down`, вместе с данными —
`docker compose down -v`.

Значения по умолчанию рассчитаны на локальный запуск. Для деплоя скопируйте
`.env.example` в `.env` и задайте как минимум `JWT_SECRET` и
`POSTGRES_PASSWORD`.

## Как устроено обучение

**Три варианта на каждом шаге.** Безопасный, спорный и опасный. Спорный — это
не «почти правильно», а отсрочка: диалог продолжается, но защиты не
появилось. Такая сетка одинакова во всех сценариях, поэтому оценки
сопоставимы между собой.

**Выбор меняет разговор, а не только счёт.** Безопасный ответ закрывает тему,
и собеседнику нечего возразить — шаги давления и повторных просьб просто не
случаются. В сценарии «Курьер просит данные карты» осторожный путь занимает
пять решений вместо восьми: отказ назвать номер карты снимает и просьбу о коде
с оборота, и угрозу отменой заказа. Именно поэтому оценка нормируется от числа
фактически сделанных выборов — иначе короткий безопасный путь выглядел бы
хуже длинного опасного.

**Объяснение вместо вердикта.** Обратная связь строится по схеме
«признак → причина → альтернатива». Слов «правильно» и «неправильно» в
контенте нет: пользователь должен унести из тренировки признак, по которому
узнает схему в реальной переписке, а не оценку своего ответа.

**Оценка.** Каждый выбор весит `+10`, `0` или `−10`. Итог нормируется от числа
фактически сделанных выборов:

```
percent = (score − min) × 100 / (max − min),   где max = 10n, min = −10n
```

Уровень: 80–100% — «устойчив», 60–79% — «внимателен», 0–59% — «уязвим».
Нижний порог намеренно 60, а не 50: пользователь, который только затягивал
диалог, не должен получать «внимателен» — уклонение от решения не является
безопасным поведением.

**Прогресс.** Динамика показывается сравнением с предыдущей попыткой по тому
же сценарию, а не графиком: это прямо отвечает на вопрос «стал ли я лучше».
Отдельно считается статистика по признакам риска — она отвечает на другой
вопрос: «какие схемы я всё ещё не распознаю». Метрики независимы: можно
набрать 75% и стабильно проваливаться на запросе кода из SMS.

Каталог признаков риска и правила написания сценариев —
[`backend/seed/README.md`](backend/seed/README.md).

## API

Контракт зафиксирован в [`api/openapi.yaml`](api/openapi.yaml) и является
единственным источником истины для фронтенда и бэкенда.

```bash
make api-docs    # документация на http://localhost:8081
make api-lint    # проверка спецификации
make api-mock    # мок-сервер на :4010 — фронтенд без бэкенда
```

Базовый префикс — `/api/v1`. Авторизация — `Authorization: Bearer <token>`;
прохождение тренировки доступно и гостю по куке `guest_session`.

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| `POST` | `/auth/register` | все | Регистрация |
| `POST` | `/auth/login` | все | Вход |
| `POST` | `/auth/refresh` | refresh-кука | Ротация пары токенов |
| `POST` | `/auth/logout` | токен | Выход с отзывом токенов |
| `GET` | `/auth/me` | токен | Текущий пользователь |
| `GET` | `/scenarios` | все | Витрина сценариев для роли |
| `GET` | `/scenarios/{code}` | все | Карточка сценария перед стартом |
| `GET` | `/scenarios/{code}/attempts` | токен | История попыток по сценарию |
| `POST` | `/sessions` | токен или гость | Старт тренировки |
| `GET` | `/sessions/{id}` | владелец | Состояние сессии и текущий шаг |
| `POST` | `/sessions/{id}/answers` | владелец | Зафиксировать выбор и получить разбор шага |
| `GET` | `/sessions/{id}/result` | владелец | Итоговый разбор прохождения |
| `POST` | `/sessions/{id}/abandon` | владелец | Прервать тренировку |
| `GET` | `/progress` | токен | Прогресс, продолжение тренировки, следующий шаг |
| `GET` | `/progress/signals` | токен | Статистика по признакам риска |
| `GET` | `/risk-signals` | все | Справочник признаков риска |
| `GET` | `/risk-signals/{code}` | все | Карточка признака риска |

Вне префикса: `GET /healthz`, `GET /readyz`, `GET /metrics`.

Ошибки приходят единым конвертом с машинным кодом — клиент принимает решения
по `error.code`, а не по тексту:

```json
{
  "error": {
    "code": "session_already_active",
    "message": "По этому сценарию есть незавершённая тренировка",
    "details": { "session_id": "3f1c9c1e-6f2a-4f7f-9a7b-6b5f2e2f1a11" }
  },
  "request_id": "01J8XQ2M7K3ZC0P4B6R9V2T5"
}
```

## Технологии

**Backend:** Go 1.25, chi (роутер), pgx (драйвер PostgreSQL без ORM), goose
(миграции), golang-jwt (access-токены), bcrypt (хеширование паролей),
log/slog (структурные логи), prometheus/client_golang (метрики), testify,
golangci-lint.

**База данных:** PostgreSQL 16.

**Инфраструктура:** Docker и Docker Compose, GitHub Actions.

**Frontend:** React 18, TypeScript, Vite, Ant Design, TanStack React Query
(серверное состояние, состояния загрузки и ошибок), Axios, React Router,
ESLint и Prettier, Vitest. Типы генерируются из контракта:
`npm run api-types` разбирает `api/openapi.yaml` в `src/api/schema.ts` —
руками они не правятся.

ORM не используется: запросы пишутся явно и параметризованно — это
предсказуемее и напрямую закрывает требование о защите от инъекций.

**Почему PostgreSQL.** Ключевые запросы приложения — агрегации по истории
попыток: средний и лучший результат, динамика, статистика по признакам риска.
Это ровно тот класс задач, где SQL с группировками даёт готовое решение.
Транзакции обеспечивают инвариант «балл сессии равен сумме баллов ответов», а
уникальный индекс по паре `(session_id, step_code)` превращает запрет менять
сделанный выбор в гарантию схемы, а не в соглашение в коде. Тело шага хранится
в JSONB — контент может эволюционировать без миграций. Развёрнутое сравнение с
MongoDB, SQLite, MySQL и Redis — в разделе 11 анализа.

```
│                          │  ├────────────────────┤  │    │
│                          │  │ service            │  │    │
│                          │  ├────────────────────┤  │    │
│                          │  │ repository         │  │    │
│                          │  └────────────────────┘  │    │
│                          │        domain            │    │
│                          │  оценка, ветвление,      │    │
│                          │  валидация контента      │    │
│                          └────────────┬─────────────┘    │
│                          ┌────────────▼─────────────┐    │
│                          │       PostgreSQL         │    │
│                          └──────────────────────────┘    │
└──────────────────────────────────────────────────────────┘
```

Монолит с тремя слоями и зависимостями только вниз: транспорт знает о
сервисах, сервисы — о репозиториях, репозитории — о БД. Обратные зависимости
запрещены и проверяются на ревью.

Доменное ядро — расчёт оценки, движок ветвления, валидатор сценариев — не
знает ни о БД, ни о HTTP. Это позволяет покрывать бизнес-логику юнит-тестами
без поднятия инфраструктуры.

На границах — DTO: доменные структуры не сериализуются в HTTP-ответ напрямую.
Это защищает от случайной утечки полей и позволяет менять домен, не ломая
контракт.

## Особенности реализации

**Контракт первичен.** OpenAPI-спецификация зафиксирована до начала
разработки. Четыре модуля писались параллельно от контракта, а не от готового
кода смежников; фронтенд может работать по мок-серверу (`make api-mock`), не
дожидаясь бэкенда.

**API не раскрывает правильный ответ.** До ответа на шаг клиент не получает
последствие варианта, его вес, обучающий комментарий и перечень признаков
риска шага. Иначе безопасный вариант вычисляется из ответа API, и тренажёр
перестаёт учить распознаванию.

**Идемпотентная фиксация выбора.** Повторная отправка ответа на уже отвеченный
шаг возвращает сохранённый результат с `already_answered: true`, не меняя
состояние и не начисляя баллы повторно. Сетевой таймаут не портит попытку.

**Инварианты вынесены в схему БД.** Уникальный индекс на паре
`(session_id, step_code)` делает запрет менять сделанный выбор гарантией
схемы. Частичный уникальный индекс допускает только одну незавершённую сессию
на сценарий. CHECK-ограничения фиксируют допустимые веса ответов.

**Контент как версионируемые данные.** Сценарии и справочник — JSON-файлы со
своей схемой. При старте они проходят структурную валидацию (девять правил:
достижимость шагов, сетка вариантов, соответствие весов, ссылки на признаки
из каталога) и заливаются в базу. Загрузка идемпотентна: версия поднимается
только при изменении содержимого файла, определяемом по хешу. Сессия
связывается с версией, на которой была начата, поэтому правка текста не меняет
результатов уже завершённых попыток. Сценарий с нарушениями не загружается, а
его ошибки попадают в отчёт с указанием места — остальной каталог при этом
загружается нормально.

**Воспроизводимая оценка.** Процент и уровень не хранятся в базе, а считаются
на лету из сохранённых ответов. Пороги уровней приходят из конфигурации, а не
из констант в коде: их изменение немедленно и одинаково отражается везде.

**Гостевые сессии.** Тренировку можно начать без регистрации: результаты
копятся за гостевым владельцем по HttpOnly-куке и переносятся на аккаунт при
первом входе или регистрации. Абстракция «владелец сессии» (пользователь либо
гость) единая для движка прохождения и аналитики.

**Ротация refresh-токенов.** Access-токен короткоживущий, refresh хранится
хешем и ротируется при каждом обновлении; выход отзывает всю сессию логина.

**Единый конверт ошибок.** Все ошибки приходят с машинным кодом и
идентификатором запроса, который совпадает с логами. Внутреннее устройство
наружу не раскрывается: ни стека, ни текста SQL.

**Наблюдаемость.** Структурные логи с идентификатором запроса и метрики
Prometheus — по HTTP-слою (число запросов, длительность) и по бизнес-событиям
(старты и завершения тренировок, распределение результатов).

**Развёртывание без ручных шагов.** Приложение не принимает трафик до
применения миграций и установления соединения с БД; проба готовности
`/readyz` учитывает состояние базы.

## Разработка

```bash
make up            # поднять приложение
make logs          # логи
make test          # тесты
make lint          # линтер
make help          # весь список команд
```

Локальный запуск API без контейнера (БД должна быть поднята):

```bash
make run
```

Демо интерфейса без готового бэкенда — фронтенд против мок-сервера Prism
(отвечает примерами из `api/openapi.yaml`, бизнес-логика не выполняется):

```bash
docker compose -f docker-compose.yml -f docker-compose.mock.yml up -d
# интерфейс на http://localhost:3000, мок на http://localhost:4010
```

Локальная разработка фронтенда (`frontend/`):

```bash
npm install
npm run dev        # http://localhost:5173, прокси /api на http://localhost:8080
# против мока вместо бэкенда:
VITE_API_PROXY_TARGET=http://localhost:4010 npm run dev
npm run typecheck && npm run lint && npm test
```

Соглашения, границы модулей и правила ревью — в [`AGENTS.md`](AGENTS.md).

## Границы MVP

**Не входит в MVP осознанно:**

- Реальная интеграция с чатами и объявлениями классифайда.
- Админ-панель для редактирования сценариев: контент поставляется файлами.
- Генерация разбора через LLM. Разбор детерминированный: он воспроизводим, не
  зависит от внешнего сервиса и не может отказать во время демонстрации.
- Мультиязычность, мобильные приложения, офлайн-режим.
- Асинхронные механики: очереди, фоновые задачи, вебсокеты.
- Ролевая модель администраторов.

## Ключевые решения

| Решение | Почему |
|---|---|
| Ветвление, а не линейный опрос | Требование кейса «показывать последствия выбора»: последствие должно менять ход диалога, иначе это викторина |
| Ровно три варианта на шаге: безопасный, спорный, опасный | Компонент диалога пишется один раз под фиксированную сетку, шкала баллов становится единой для всего контента |
| Шкала `+10 / 0 / −10` | Исключает несопоставимость оценок между сценариями и делает пороги уровней универсальными |
| Нормировка от числа сделанных выборов | При ветвлении «лучший путь» неоднозначен; выбранный подход не зависит от структуры графа |
| Порог «внимателен» — 60%, а не 50% | При 50% пользователь, только затягивавший диалог, попадал бы во «внимателен». Это неверное сообщение |
| Сценарии — данные, а не код | Контент пишется параллельно движку, добавление сценария не требует релиза |
| Версионирование сценариев | Правка контента не меняет результатов уже завершённых сессий |
| Гостевое прохождение с переносом прогресса | Тренировку видно до регистрации, а результаты не теряются: барьер входа снят без потери персонализации |
| Разбор без LLM | Воспроизводимость и отсутствие внешних зависимостей на демонстрации |
| Четыре экрана | Прогресс встроен в главную, история — в экран результата: минимум роутов при одном фронтенд-разработчике |

Полные формулировки и альтернативы — в [`Сase-analysis.md`](Сase-analysis.md).
